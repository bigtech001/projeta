## Services

| Service | Port | Path prefix | Protocol |
|---------|------|-------------|----------|
| API Server | 8080 | `/api` | HTTP + WebSocket (`/ws`) |
| Frontend | 20976 | `/` | HTTP (Vite dev server) |

Both services are proxied through a shared reverse proxy at port 80. All API calls from the frontend use relative URLs — no hardcoded `localhost` references.

## Projection System

**Flow:**
1. Operator clicks a verse → `POST /api/projection/control { action: "show_song", songId, verseIndex }`
2. `projection.ts` route loads the song, calls `parseLyrics()` to split verses, builds the update payload (currentVerseLine, nextVerseLine, totalVerses)
3. DB row updated → `broadcastProjectionUpdate(state)` emitted to all WebSocket clients
4. Projection window receives WebSocket message → re-renders with AnimatePresence transition (fade / slide / scale)
5. Fallback: all clients poll `/api/projection/state` every 2 seconds if WebSocket is unavailable

**Supported actions on `POST /api/projection/control`:**

| action | Effect |
|--------|--------|
| `show_song` | Set mode=song, load verse content, broadcast |
| `next_verse` | Advance verse index, broadcast |
| `prev_verse` | Rewind verse index, broadcast |
| `blank` | Set isActive=false, mode=blank, broadcast |
| `show_bible` | Set mode=bible with verse text+reference, broadcast |
| `show_announcement` | Set mode=announcement with text, broadcast |
| `play_audio` / `pause_audio` / `stop_audio` | Toggle isAudioPlaying flag |
| `set_volume` | Update audioVolume (0–100) |
| `set_liturgy` | Attach a liturgy ID to the current session |

**Lyric parsing** (`lib/parse-lyrics.ts`):
- Splits on double newlines
- Detects label lines (`verso`, `coro`, `refrão`, `bridge`, etc.) and strips them from display content
- Two exported functions: `parseLyrics` (returns `string[][]`) and `parseLyricsWithLabels` (returns structured verse objects with index+label)

## Stage Screen

Standalone popup window (`/stage`) meant to be shown on a second monitor facing the worship team.

- **Top bar**: pulsing live indicator + live clock (HH:MM:SS via `useClock` hook)
- **Main area**: Large current verse text / bible verse, dimmed next verse preview
- **Announcement banner**: Amber overlay when mode=announcement
- **Bottom bar** (3 columns):
  - Worship timer: local stopwatch with play/pause/reset (independent of projection state)
  - Current song or bible reference
  - Next liturgy item (type + estimated duration)

The stage screen reads projection state via the same WebSocket + polling fallback as the operator.

## Operator System

Main control surface (`/operator`). Full-height three-column layout:

**Left column — Song list**
- Live search (debounced via React Query key)
- Single-click: select song (load verses without projecting)
- Double-click (or MonitorPlay icon): open Playback Mode dialog, then project

**Center column — Verse grid**
- All verses displayed as cards; active verse highlighted with border+scale
- Click any verse to jump directly to it
- Prev/Next buttons + keyboard shortcuts

**Right column — Audio + Quick Actions**
- Play/Pause/Stop audio controls (disabled when mode = Somente Letras)
- Volume slider (0–100, synced to projection state via `set_volume` action)
- Liturgy progress tracker (up to 5 items, current highlighted)
- Quick action buttons: announcement, blank, open projection window, open stage

**Keyboard shortcuts** (blocked when focus is on an input):

| Key | Action |
|-----|--------|
| `→` / `↓` | Next verse |
| `←` / `↑` | Previous verse |
| `Space` / `Esc` | Blank projection |
| `F` | Focus song search |
| `P` | Open projection window |
| `S` | Open stage monitor |
| `?` | Toggle shortcuts help dialog |

**Playback Mode dialog** (on double-click):
1. Somente Letras — lyrics only, audio controls disabled
2. Letras + Playback — lyrics + audio controls visible
3. Letras + Áudio Cantado — lyrics + full MP3 from linked file

## Audio System

**Server-side:**
- MP3 files stored in `config/musicas/` (gitignored, server filesystem)
- `GET /api/audio/files` — lists all `.mp3` files, cross-references with DB songs by title match, returns `{ filename, title, path, songId | null }`
- `POST /api/audio/scan` — iterates all `.mp3` files, matches by title (case-insensitive), updates `songs.mp3Path` via `eq(id)` (exact match by ID to avoid partial updates)

**Client-side:**
- Projection state stores `isAudioPlaying` and `audioVolume`
- Audio play/pause/stop dispatched to `/api/projection/control` and broadcast so all clients stay in sync
- Volume controlled via Slider in Operator → `set_volume` action

## Settings Persistence

All settings are stored entirely in `localStorage` under key `cl-settings` as a JSON blob. No server-side settings table. Settings survive browser refresh and are shared across all same-origin windows (operator, stage, projection popup) without any synchronization overhead.

**`AppSettings` shape:**

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `churchName` | string | "Minha Igreja" | Shown in sidebar header |
| `congregationName` | string | "Congregação Central" | Sub-label |
| `logoUrl` | string\|null | null | Base64 data URL of uploaded logo |
| `projectionFontSize` | small/medium/large/xl | "large" | Font size on projection screen |
| `projectionBackground` | black/dark-blue/gradient | "black" | Projection background style |
| `projectionTransition` | fade/slide/scale | "fade" | AnimatePresence transition style |
| `audioEnabled` | boolean | true | Enables audio playback features |
| `audioDefaultVolume` | number 0–100 | 75 | Initial volume for new sessions |
| `theme` | dark-blue/worship-purple/light-modern | "dark-blue" | UI theme |
| `musicasFolder` | string | "config/musicas" | Informational — path shown in settings |

**Theme persistence:** theme ID also written to `localStorage["cl-theme"]` separately so `ThemeProvider` can read it synchronously before first render (avoids flash of wrong theme).

**`useSettings` hook:** not a context — each component gets independent state initialized from `localStorage`. Changes in one component (e.g. Settings page) are immediately persisted to `localStorage` and will be picked up on next navigation/mount by other components.

## Local Music Indexing

1. Operator/admin drops `.mp3` files into `config/musicas/` on the server
2. In Settings → Pasta de Músicas, click **Escanear e Vincular**
3. Server calls `POST /api/audio/scan`:
   - Reads directory listing
   - Strips `.mp3` extension, replaces `-` and `_` with spaces to get candidate title
   - Case-insensitive match against all song titles in DB
   - Updates `songs.mp3Path` for each match (using `eq(id)` for safety)
   - Returns `{ scanned: N, linked: N }`
4. `GET /api/audio/files` shows current link status for each file

## Offline-First Compatibility

| Feature | Mechanism |
|---------|-----------|
| Settings | `localStorage` — works with no network |
| Theme | `localStorage` — applied synchronously before render |
| Song/collection/liturgy data | React Query cache (30s stale time) + browser cache |
| Projection state | WebSocket primary; 2s polling fallback if WS fails |
| Bible books list | In-memory server response, cached by React Query |
| API availability | All mutations degrade gracefully with React Query retry (1 retry) |

For a fully offline Electron deployment, the Express server would be embedded in the Electron main process, eliminating all network dependency.

## Electron Desktop Conversion Notes

The codebase is structured to support Electron with minimal changes:

**Already compatible:**
- No hardcoded `localhost` URLs in frontend code (all relative via `BASE_URL`)
- `localStorage` works in Electron's renderer process
- `window.open()` for projection/stage popups works in Electron (creates new `BrowserWindow`)
- `requestFullscreen()` API works in Electron
- `window.location.protocol` detection in WebSocket hook handles `file:` and `app:` schemes

**Changes needed for Electron packaging:**
1. **Main process**: Start Express server as a child process or embedded module; pass chosen port to renderer via `contextBridge`
2. **WebSocket URL**: In `use-websocket.ts`, detect Electron environment and connect to `ws://localhost:{PORT}/ws` directly instead of using `window.location.host`
3. **BASE_URL**: Set `base: '/'` in Vite config for production build; use `loadFile()` in Electron to load `dist/index.html`
4. **MP3 files**: Map `config/musicas/` to a user-writable path via `app.getPath('userData')`
5. **Window management**: Use Electron's `BrowserWindow` API with `nodeIntegration: false` and `contextIsolation: true` for security
6. **Auto-updater**: Add `electron-updater` for OTA updates

```bash
pnpm --filter @workspace/api-spec run codegen
# Then verify lib/api-zod/src/index.ts exports only ./generated/api (not ./generated/api.schemas)
```

- `lib/api-zod/src/generated/api.ts` — Zod validation schemas
